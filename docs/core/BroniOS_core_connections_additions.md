**Требование к ядру: отказоустойчивость внешних каналов.** Ни один внешний сервис (ВК, Google, AppEvent) не может быть единственным путём брони. Окно по ссылке работает всегда; недоставленное сообщение ВК дублируется другим каналом; сбой чтения календаря даёт тревогу, а не молчание; отключение внешнего сервиса ничего не ломает у броней.

## Опора (решено раньше)

- «Призраки»: чужой календарь только на чтение, время занято (блок 4); запуск из мастера подключения (блок 26).
- Импорт истории из Google: только зал и время, статус «прошедшая», источник «импорт» (блок 10, принято ядром).
- Два режима виджета и тема студии на сервере (блок 13). Окно брони по адресу на зал (блок 9).
- Источник брони — поле брони (блок 4). Согласие хранит адрес страницы и источник (блок 16).
- Пересечения проверяет сервер; конфликт показывается человеку (блок 4).

## К1. Связь «зал ↔ внешний календарь»

- Запись подключения: студия, зал (или «вся студия»), тип (`google_oauth` | `ics_url`), направление (`out` | `in_busy` | `import_once`), кто подключил, когда, состояние (работает / ошибка с текстом / отключено), время последнего успешного чтения.
- У зала может быть одно `out` в Google и несколько `in_busy` (например, тот же Google-календарь, куда пишет AppEvent, и личный календарь хозяина).
- Секреты (токены Google, адрес .ics с секретом внутри) — в закрытой части, не отдаются в API никому, даже хозяину (показываем «подключено к …@gmail.com»).

## К2. Наружу: лента .ics для подписки (новое, приоритет НИЗКИЙ после слов Алексея 09.10)

Значит, для «Томсона» Google уже закрывает «смотреть в телефоне»; лента нужна только тем, у кого нет доступа к Google студии. Не строить в первой волне, пока студии не попросят (вывод).


- Ядро отдаёт ленту `.ics` по секретному адресу: на студию, на зал, на сотрудника (видит только залы, к которым у него есть доступ).
- Адрес содержит длинный случайный ключ; «Сбросить ссылку» выдаёт новый, старый сразу перестаёт работать. Сброс — автоматически при снятии роли сотрудника (предложение).
- Содержимое события: зал, статус, время (моменты с часовым поясом зала), ссылка на бронь в админке, **Имя, Телефон, Примечание** (решено Алексеем 09.10, см. К4). Лента — только для сотрудников, у каждого своя секретная ссылка; публичной ленты нет. Закрытия залов идут как «Закрыто» без причины. Пробные брони — с пометкой «проба». Отменённые и «не пришли» из ленты исчезают.
- Закрытия залов (блок 20) идут в ленту как «Закрыто», без причины. Пробные брони (блок 26) — с пометкой «проба».
- Отменённые и «не пришли» из ленты исчезают.
- Факт для ожиданий: Google обновляет подписку по ссылке редко, «несколько часов, до суток» (сторонний источник nocal.app; не проверено). Лента — для просмотра, не для срочного.

## К3. Внутрь: «призраки» из Google (приоритет) и .ics (запасной путь)

- **AppEvent = Google.** По словам Алексея (09.10) AppEvent подключается к студии через Google Календарь, поэтому его брони приходят «призраками» через обычное подключение Google, особой ленты для AppEvent не нужно. Не проверено: в какие календари AppEvent пишет, читает ли он время, занятое BroniOS, что кладёт в описание.

- `ics_url`: сервер читает ленту по расписанию (предложение: раз в 10–15 мин; с условными запросами, чтобы не тянуть неизменённое — вывод), берёт только интервалы «занято» и UID события. Название, описание, участников **не хранит**.
- `google_oauth`: чтение через API + подписка на уведомления. По документации Google уведомление приходит без содержимого («что-то изменилось»), адрес приёма только HTTPS с действительным сертификатом под домен, канал истекает и продлевается вручную новым запросом `watch`. Нужен планировщик продления (блок 6).
- Призрак = блокировка времени с источником «внешний календарь X», не бронь: не списывает токен, не идёт в статистику продаж, не редактируется в BroniOS.
- Пересечение призрака с уже существующей бронью (пришло позже) → запись во «Входящие → Внимание» администратору, ничего не двигается само.
- Ошибка чтения дольше часа → тревога хозяину «Календарь не обновлялся с 14:05» (иначе студия думает, что защищена, а она нет — вывод).
- Призраки — только на чтение. Записывать в чужие календари по паролю (CalDAV Яндекса и iCloud требуют пароль приложения: справка Яндекса; для iCloud — сторонний источник) **не предлагаем**: хранить чужие пароли не хотим (вопрос Алексею 5).

## К5. ВКонтакте

Этап 1 (ничего от ядра, кроме мелочи):
- Метка источника в адресе окна (`?from=vk`, вообще `?from=<метка>`) → поле «источник» брони. Нужен список допустимых меток и правило: неизвестная метка = «сайт».

Факт (скриншоты Алексея 09.10): AppEvent у «Томсона» уже стоит в сообществе ВК как приложение-плитка и открывается внутри ВК; для BroniOS это тот же путь. Цены залов дублируются в «Товарах» ВК (Алексей 09.10: «цены в товарах в VK меняются вручную»; автообновления нет, ядру ничего делать не нужно).

Этап 2 (мини-приложение BroniOS, одно на платформу; регистрация только словом Алексея):
- Привязка студии к сообществу: `vk_group_id` у студии; одно сообщество — одна студия. Узнаём при установке (VKWebAppAddToCommunity возвращает `group_id`, dev.vk.ru).
- Проверка подписи параметров запуска VK **на сервере** (обязательна по правилам VK Mini Apps). Из параметров запуска берём `group_id` → студию, `vk_user_id` → контакт клиента «ВКонтакте».
- Телефон из VK (VKWebAppGetPhoneNumber возвращает номер и подпись) — сервер проверяет подпись и принимает номер как подтверждённый VK. Можно ли тогда считать номер «проверенным» для входа клиента без кода — вопрос ядру.
- Разрешение «сообщения от сообщества» (VKWebAppAllowMessagesFromGroup, работает только после модерации приложения) → у клиента в брони отметка «можно писать в VK от сообщества студии». Ядру нужен канал доставки «VK от имени сообщества» рядом с почтой и пушем (блок 6): ссылка на бронь, напоминание, ответ администратора. Для этого студия выдаёт ключ доступа сообщества; хранение — закрытая часть. **Это бесплатный канал для «потерял ссылку»** (блок 1, вопрос 6) — вывод, не проверено на деле.
- Требования VK, которые касаются ядра: пользовательское соглашение и политика у приложения; бесплатное удаление данных пользователя по его запросу; разные права у админов сообщества и подписчиков (роль «админ сообщества VK» ≠ роль студии; права в BroniOS даёт только ядро — вывод).
- Внутри VK страница брони открывается в приложении (правила VK против увода на сторонние ресурсы; вывод, ждёт Алексея — вопрос 4).
- Согласие (блок 16): источник «VK, сообщество N».

Этап 3 (позже): виджет сообщества «Свободно сегодня» — ядру нужен открытый запрос «ближайшие свободные окна по залам на сегодня» (уже есть «свободные окна» в блоке 9, нужен короткий вид).

## К6. Код для чужих сайтов

- **Ключ встраивания = только публичный номер студии и зала.** Никаких секретов в коде (урок `STUDIO_KEY` в открытом `index.html`).
- **Список разрешённых сайтов студии** (домены) вводится студией при регистрации на сайте BroniOS, на шаге «Сайт». **Решено (Алексей, 09.10, дословно): «6 нужна связка, клиент регистрируется на нашем сайте, указывает адрес сайта, защита от мошенников нужна».** Код выдаётся только зарегистрированной студии и работает только на её адресах; ядро отдаёт окно с `Content-Security-Policy: frame-ancestors <список>` и проверяет `Origin` при создании брони (стандарт браузеров; на нашем окне не проверено). **Решено (Алексей, 09.10, дословно): «AppEvent так не делает, но по сути это и не нужно. AppEvent делает код виджета и его встраивают себе на сайт. Если это фишинговый сайт или сайт клон, наши меры защиты от этого не уберегут. Клиенты приходят на сайт по локичному пути, через рекламу, соц сети, агрегаторы.»** Значит: **подтверждения владения сайтом нет**, только список адресов, введённый студией. Ядру: хранить домены студии; тревога хозяину студии при смене адреса (предложение). Открытый вопрос, не решён: студия-самозванец под чужим названием (онбординг, блок 26, и юрист).
- **Источник = адрес страницы**, где стоит окно, → поле брони и запись согласия (блок 16), и в статистику «брони по сайтам».
- **Цена, часы работы, свободность считаются только на сервере** (блоки 11, 15). Окно присылает лишь выбор клиента.
- **Ограничение заявок** с одного устройства/адреса в час (число задаёт ядро). Платной капчи нет.
- **Тема студии** отдаётся открытым запросом по номеру студии; кэш короткий, чтобы смена цвета доходила до сайтов быстро (минуты).
- **Скрипт-загрузчик** (одна строка) и запасной iframe. Скрипт: ставит окно, подстраивает высоту (окно сообщает высоту сайту — уже в сценарии брони), открывает страницу брони отдельной вкладкой. Работа BroniOS, ядру — только отдавать скрипт и тему с адреса в России (данные клиентов в России, решение 2 Б: боевое в Яндексе).
- **Свой поддомен студии** (`бронь.томсон.рф`) нужен для надёжной плашки «Ваша бронь» на iPhone (сценарий брони, не проверено). Это значит: студия ставит запись в своём DNS, платформа выпускает сертификат на этот поддомен. Вопрос ядру, можно ли это в Яндекс Облаке без платных сервисов (не проверено).
- Режим «подключён к сайту платформы / сам по себе» (блок 13) от кода не зависит: код один, режим меняет только откуда берутся услуги и цены.
